# 2503.13657: Why Do Multi-Agent LLM Systems Fail?

## Paper

1. **Problem and claim.**
   (a) Targets multi-agent LLM systems with minimal gains over simple baselines. Claims failures come mostly from system design, agent coordination and weak verification, not only model limits. No direct study of memory or long runs.
   (b) "MAS failure is not merely a function of challenges in the underlying model; a well-designed MAS can result in performance gain"
   (c) Section 4, Insight 1 (page 7).

2. **Mechanism.**
   (a) Agents remember nothing here. MAST is a text taxonomy: 14 failure modes in 3 categories, mapped to pre-, during-, post-execution stages; built by grounded-theory reading of 150 traces, applied by an LLM judge.
   (b) "MAST, illustrated in Figure 1, identifies 14 fine-grained failure modes, which we map to MAS execution stages (Pre-Execution, Execution, and Post-Execution)"
   (c) Section 4 (page 7).
   Modes (category share of 1642 traces):
   - FC1 Design 44.2%: 1.1 Disobey Task Spec; 1.2 Disobey Role Spec; 1.3 Step Repetition; 1.4 Loss of Conversation History; 1.5 Unaware of Termination Conditions.
   - FC2 Misalignment 32.3%: 2.1 Conversation Reset; 2.2 Fail to Ask Clarification; 2.3 Task Derailment; 2.4 Information Withholding; 2.5 Ignored Other Agent's Input; 2.6 Reasoning-Action Mismatch.
   - FC3 Verification 23.5%: 3.1 Premature Termination; 3.2 No or Incomplete Verification; 3.3 Incorrect Verification.

3. **Evidence.**
   (a) 1642 annotated traces, 7 frameworks. Human kappa 0.88; few-shot o1 judge kappa 0.77. ChatDev role-prompt fix +9.4%; added task-level verification +15.6%.
   (b) "analysis reveals 41% to 86.7% failure rate on 7 state-of-the-art (SOTA) open-source MAS"
   (c) Section 1 (page 2); Section 3.3.

4. **Limits the authors admit.**
   (a) Taxonomy is not exhaustive. Prompt and topology fixes help only a little; completion stays low. Memory and state management are left as open research.
   (b) "we do not claim it covers every potential failure pattern"
   (c) Section 1 (page 2); Section 5.3.

5. **(inferred) What Goals could take from it.**
   - Keep a plain `failure-modes.md` of the modes that fit long single-agent runs (1.1, 1.3-1.5, 2.1, 2.3, 2.6, 3.1-3.3): definition plus one real example each.
   - At phase end, a fresh-context judge prompt (hook) answers yes/no per mode with evidence, appended to `failure-log.jsonl`; counts show change from run 1 to 100.
   - Keep a "done steps" ledger in the plan file; a hook warns on repeats. After a reset, re-inject plan and decisions first.
   - Each phase states "done when" plus a proof command; close only after a low-level and a goal-level check.

## Code

Repo: https://github.com/multi-agent-systems-failure-taxonomy/MAST

6. **Repo facts.** No license file. Language: one Python notebook; the rest is data. Folders: `assets`, `inter_annotator_agreement_annotations`, `taxonomy_definitions_examples`, `traces`. Of 13,373 tracked files, 13,358 are raw traces (AG2 7184, MagenticOne_GAIA 4535, rest under 650 each). README says it holds the paper's code and data and links the full dataset on Hugging Face. In practice: data plus one notebook, no library.

7. **Where the logic lives.**
   - `llm_judge_pipeline.ipynb`: judge prompt, o1 call, yes/no parsing.
   - `taxonomy_definitions_examples/definitions.txt`: 14 definitions for the judge.
   - `taxonomy_definitions_examples/examples.txt`: few-shot examples per mode.
   - `inter_annotator_agreement_annotations/*.pdf`: human labels.
   - No memory or adaptation code exists.

8. **How stored.** Definitions and examples are plain text pasted into one prompt. Judge replies become a dict of mode id to 0/1 list, pickled.
   [llm_judge_pipeline.ipynb:211] <<"    failure_modes = {\n",>>
   [taxonomy_definitions_examples/definitions.txt:25] <<Unexpected context truncation, disregarding recent interaction history and reverting to an antecedent conversational state.>>

9. **Prompts and policies.** One prompt: yes/no per mode, evidence required, o1 at temperature 1.0, over-long traces cut.
   [llm_judge_pipeline.ipynb:27] <<"    model='o1',\n",>>
   [llm_judge_pipeline.ipynb:159] <<"            full_trace_list[i] = full_trace_list[i][:1048570 - len(examples)]\n",>>

10. **Paper vs code.**
   - Code names 3.2 'No or Incorrect Verification' and 3.3 'Weak Verification'; paper: incomplete, incorrect.
   [llm_judge_pipeline.ipynb:64] <<"    \"3.2 No or Incorrect Verification: <yes or no>\"\n",>>
   - Sample answer lists nonexistent modes 1.6, 2.7; parser defaults missing modes to "no".
   - Not in repo: `agentdash` package, kappa code, intervention code (only traces).
   - README names dataset `mcemri/MAD`; paper says `mcemri/MAST-Data`.
