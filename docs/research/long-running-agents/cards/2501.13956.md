# 2501.13956: Zep: A Temporal Knowledge Graph Architecture for Agent Memory

## Paper

1. Problem and claim: Agents need memory of changing conversations and business data that cannot fit in the context window; static RAG fails. Claim: a temporal knowledge graph (Graphiti, inside Zep) beats MemGPT on DMR and full-context on LongMemEval, with lower latency.
   - Quote: "they will need access to a large corpus of continuously evolving data"
   - Where: Section 1 Introduction

2. Mechanism: Three graph tiers: episodes (raw messages, text, JSON), entities with fact-edges (LLM-extracted at ingest from the last 4 messages), and community summaries. Edges carry four timestamps. A new contradicting fact sets the old edge's end time; nothing is deleted.
   - Quote: "it invalidates the affected edges by setting their tinvalid to the tvalid of the invalidating edge"
   - Where: Section 2.2.3 Temporal Extraction and Edge Invalidation

3. Evidence: DMR 94.8% vs MemGPT 93.4% (gpt-4-turbo). LongMemEval: Zep 63.8% (gpt-4o-mini) and 71.2% (gpt-4o) vs full-context 55.4% and 60.2%. Context 1.6k tokens vs 115k; latency about 3 s vs about 30 s.
   - Quote: "Zep achieves substantial results with accuracy improvements of up to 18.5% while simultaneously reducing response latency by 90%"
   - Where: Abstract; Section 4.3.2, Table 2

4. Limits the authors admit: Worse on single-session-assistant questions (down 9% to 18%). Dynamic community updates drift and need periodic refreshes. DMR is too easy. MemGPT could not be run on LongMemEval.
   - Quote: "suggest further research and engineering work is needed"
   - Where: Section 4.3.2, after Table 3

5. (inferred) What Goals could take:
   - Keep decisions and proof as dated fact lines in a plain file, each with valid_from, invalid_at and a source pointer. Never delete; a new decision sets the old line's invalid_at.
   - A Stop or PreCompact hook prompt compares each new fact to related old facts and marks a contradiction only if both cannot be true (reuse Graphiti's wording).
   - A SessionStart hook injects only facts with no invalid_at, capped near 20 lines (Zep used about 1.6k tokens).
   - Keep an append-only raw log (the episode layer) so summaries stay traceable.
   - Resolve "next Thursday" to absolute dates when writing.

## Code

Repo: https://github.com/getzep/graphiti

6. Repo facts: Apache 2.0 LICENSE. Python (graphiti-core 0.31.2). Folders: graphiti_core, server, mcp_server, examples, tests, spec, signatures. README presents a usable library plus a REST server and MCP server; the paper's DMR and LongMemEval experiments are not included.

10. Paper vs code:
   - In the repo: all three tiers; valid_at, invalid_at, created_at, expired_at on edges (plus reference_time); LLM duplicate and contradiction check; label-propagation communities; BM25, cosine and BFS search; RRF, MMR, node-distance, episode-mentions and cross-encoder rerankers; the facts-with-date-range context string. Extras not in the paper: sagas, Pydantic ontologies, remove_episode, future-tense date rules.
   - Only in Zep's commercial service (README): users, threads, memory API, Konig graph database, dashboard, governance, managed business-data ingestion.
   - Only in the paper: the DMR and LongMemEval runs behind the headline numbers (repo has just a graph-building eval on longmemeval_oracle; promised notebooks absent), BGE-m3 models, and the entity reflection step (grep finds none).
   - Differs: paper uses the last 4 messages; code uses 10 previous episodes in add_episode and 3 by default in retrieve_episodes. store_raw_episode_content=False can blank episode text, weakening "non-lossy".
