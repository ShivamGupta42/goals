# 2409.07429: Agent Workflow Memory

## Paper
1. Problem and claim: (a) Agents solve each task from scratch and never reuse routines from past runs, so they fail on long-horizon tasks. Claim: inducing reusable workflows from past trajectories into memory improves success and efficiency. (b) "as agents solve each task separately, they do not learn from past successes and failures, and are therefore unable to adapt over time" (c) Section 1 Introduction.
2. Mechanism: (a) Text workflows (description plus steps: state description, reasoning, action), induced by an LM from trajectories an LM judge marked successful, example values replaced by variables. Online: added to memory after each task; offline: induced once from training data. No forgetting described. (b) "These workflows are segmented (based on double-line breaks in the model output) and stored separately in the workflow memory." (c) Section 2.3.
3. Evidence: (a) WebArena (GPT-4, online): 35.5% success vs 23.5% BrowserGym; 5.9 steps vs 7.9 for the ax-tree variant. Mind2Web cross-task step success 45.1 vs 36.2 (MindAct). Gain appears within about 40 examples. (b) "AWM substantially improves the baseline results by 24.6% and 51.1% relative success rate on Mind2Web and WebArena" (c) Abstract; Tables 1 and 3.
4. Limits: (a) No limitations section. Admitted: online induction can write wrong workflows from wrong trajectories; offline plus online workflows do not add up; agents struggle to deviate from a workflow when the page differs. (b) "not always correct, thus can lead to incorrect workflows that degrade model performance" (c) Section 3.2.2 (also 3.2.1, Appendix C).
5. (inferred) What Goals could take:
   - One plain file per goal, `workflows.md`: name, when to use, steps with placeholders. Read it in a SessionStart or UserPromptSubmit hook.
   - Write it only after a phase passes its proof check; a Stop hook runs an induce prompt on that phase. This copies AWM's judge gate; wrong workflows were its stated failure.
   - Keep it small: the paper averaged 7.4 workflows per site, and more context hurt (NL plus HTML scored lower). Set a size cap.
   - Add what AWM lacks: log which workflow each phase used and drop unused ones.
   - Tell the agent to diverge when the state differs.
   - Seed new goals from old workflows only as labelled, optional hints.

## Code
Repo: https://github.com/zorazrw/agent-workflow-memory
6. Repo facts: Apache 2.0 LICENSE. Python. Folders `webarena/`, `mind2web/`, `assets/`. README says it holds the paper's experiments (WebArena and Mind2Web, offline and online), not a general library.
7. Where the logic lives:
   - `webarena/pipeline.py`: online loop (run task, autoeval, re-induce).
   - `webarena/induce_prompt.py`: LM induction, writes the workflow file.
   - `webarena/induce_rule.py`: rule-based induction (dedup, optional manual approve).
   - `webarena/agents/legacy/agent.py`: injects workflow file into the system prompt.
   - `mind2web/online_induction.py`: Mind2Web induction from past results.
   - `mind2web/workflow/retrieve.py`: standalone FAISS retrieval over workflows.
8. Storage: one plain-text file per website, overwritten on each induction; no database.

9. Prompts and policies: induce only from trajectories the evaluator accepted, keep one per task template; the prompt asks for non-overlapping sub-routines of at least two steps with variable names.

10. Paper vs code:
   - Code regenerates the whole workflow file from all past successful runs each time and never reads the old file.
   - The whole file goes into the prompt. FAISS retrieval exists but the pipelines do not call it.
   - Mind2Web online induction reads every result file with no judge check (`mind2web/online_induction.py`); WebArena does gate (`--criteria autoeval` or `gt`).
   - WebArena induction samples at temperature 1.0 [webarena/induce_prompt.py:94] <<temperature=1.0,>>; the paper reports 0.0. Its two benchmarks use different prompt files.
   - Not in code: the workflow-as-action variant, the quality metrics, the offline plus online mix.
