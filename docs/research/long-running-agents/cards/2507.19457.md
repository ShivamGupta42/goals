# 2507.19457: GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning

## Paper

1. Problem and claim: (a) Adapting an LLM system to a task is slow when weights cannot change and rollouts are costly. Claim: reflecting on traces in plain language and editing prompts beats RL with far fewer rollouts. No long-run memory or context treatment. (b) "many downstream LLM applications invoke expensive tool calls, have limited inference budget for sampling from the LLM itself, or simply cannot finetune the weights" (c) Section 1 Introduction, p.2.

2. Mechanism: (a) Prompt text only; weights frozen. Pool keeps candidates, parents, per-task scores. Each step samples a non-dominated candidate, reflects on minibatch traces and feedback, rewrites one module prompt, keeps it if minibatch score improves; dominated ones stop being sampled. (b) "a reflection LM is then shown the (current prompt, language program trajectory, score, feedback) with the task to reflectively attribute successes or failures" (c) Section 3, Reflective Prompt Mutation, p.5.

3. Evidence: (a) Qwen3 8B, six tasks: GEPA beats GRPO (24,000 rollouts) by 6% on average, up to 20%. Aggregate gain +9.62 vs GRPO +3.68. GPT-4.1 Mini: +12.19 vs MIPROv2 +5.64. Pareto selection +12.44 vs greedy +6.05. (b) "Across six tasks, GEPA outperforms GRPO by 6% on average and by up to 20%, while using up to 35x fewer rollouts." (c) Abstract, p.1; Tables 1-3.

4. Limits the authors admit: (a) No limitations section. Admitted in passing: most rollout budget goes to validation scoring; Merge hurt Qwen3 8B and needs tuning; kernel-search results are early. Nothing on forgetting or long runs. (b) "However, these are early results and warrant further systematic study." (c) Section 5.1, p.12.

5. (inferred) What Goals could take:
- Keep the goal's working instruction file as versions (`versions/003.md`, header `parent: 001`). After each phase, a reflection prompt reads the phase trace plus the proof-check text (failed criteria, error output, not just pass/fail) and rewrites one section.
- Gate: a hook keeps the new version only if the next proof check beats its parent. Otherwise keep the parent and log the failure.
- Keep a small JSON score table (version by task). Start the next phase from a version that is best on at least one task, not always the latest best, so one lucky version cannot lock in.
- Reuse the meta-prompt line [src/gepa/strategies/instruction_proposal.py:164] <<Identify all niche and domain specific factual information about the task and include it in the instruction, as a lot of it may not be available to the assistant in the future.>> for the handoff note before a context reset.
- Caveat: GEPA needs many scored repeat runs. Apply it only to recurring task kinds. Validation scoring is the main cost.

## Code

Repo: https://github.com/gepa-ai/gepa

6. Repo facts: LICENSE is MIT (README badge says MIT). Python (>=3.10). Top-level: `src/`, `tests/`, `examples/`, `docs/`, `assets/`, `.github`, `.claude`, `.claude-plugin`. README presents a usable library (`pip install gepa`, [README.md:6] <<Optimize any text parameter>>); paper experiments live in a separate gepa-artifact repo.

7. Where the logic lives:
- `src/gepa/core/state.py`: GEPAState, the candidate pool, lineage, scores, Pareto maps, save and resume.
- `src/gepa/gepa_utils.py`: dominated-candidate pruning and frequency-weighted Pareto sampling.
- `src/gepa/strategies/instruction_proposal.py`: the reflection prompt template and output parser.
- `src/gepa/proposer/reflective_mutation/reflective_mutation.py`: sample parent and minibatch, build feedback dataset, propose, re-evaluate.
- `src/gepa/strategies/acceptance.py`: accept or reject a child after the minibatch.
- `src/gepa/proposer/merge.py`: system-aware merge of lineages that share an ancestor.

8. How it is stored:
[src/gepa/core/state.py:232] <<program_candidates: list[dict[str, str]]>>
[src/gepa/core/state.py:246] <<program_at_pareto_front_valset: dict[DataId, set[ProgramIdx]]>>
[src/gepa/core/state.py:451] <<self._atomic_write_json(run_dir, "candidates.json", self.program_candidates)>>

Each candidate is a dict of component name to prompt text; parents, per-validation-example scores and Pareto sets sit in parallel lists. With `run_dir` set, it writes `gepa_state.bin` (pickle, used for resume), `candidates.json`, `run_log.json`.

9. Prompts and policies:
[src/gepa/strategies/instruction_proposal.py:160] <<Your task is to write a new instruction for the assistant.>>
[src/gepa/strategies/acceptance.py:53] <<return new_sum > old_sum>>
[src/gepa/gepa_utils.py:134] <<curr_prog_id = rng.choice(sampling_list)>>

The default prompt matches the paper's Appendix C meta-prompt. Components rotate round-robin; the template is configurable.

10. Paper vs code: Benchmarks, GRPO and MIPROv2 baselines are not in this repo. Code adds frontier types (instance, objective, hybrid, cartesian), epsilon-greedy and current-best selectors, `skip_perfect_score`, resume from disk, image-aware reflection, `optimize_anything`, and `gskill` (learns skill files for coding agents). Merge is off by default (`use_merge`). Default reflection minibatch is 3; the paper's main text does not give it.
